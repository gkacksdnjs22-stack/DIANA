DIANA 기기 연결 및 파일 암호화

사용 흐름
PC에서 기존 6자리 코드 생성 → 휴대폰 입력 → PC의 기기 이름 확인 및 승인/거절 → 연결 완료.
코드만 맞힌 요청에는 연결 토큰을 발급하지 않는다. 요청은 코드의 5분 만료를 계승한다.
긴 비밀키 입력, QR, 문서별 암호 입력은 없다. 연결 키 생성·교환·보호 저장과 파일 암호화는 자동이다.
기기 이름은 휴대폰이 보낸 표시 문자열이며 검증된 기기 신원이 아니다.
연결 승인과 개별 문서 작업 승인은 별개다. 기존 PC 문서 권한과 명시적 승인 정책은 그대로 유지한다.

암호화
P-256 ECDH와 HKDF-SHA256으로 기기별 32바이트 키를 만들고 HMAC-SHA256으로 동일 키를 확인한다.
개인키와 공유 키는 서버에 보내지 않는다. PC는 Windows CurrentUser DPAPI로 저장하고,
Android는 Android Keystore의 AES-256-GCM 키로 세션 및 대기 중인 개인키를 암호화해 저장한다.
새 연결은 새 키를 사용하며, 키를 잃은 경우 재연결한다. 서버에 복호화 키를 백업하지 않는다.
파일마다 무작위 AES-256-GCM 데이터 키와 96비트 nonce를 만들고 기기 키로 데이터 키를 감싼다.
전송 ID·방향·파일명·원문 해시·길이는 인증된 추가 데이터에 포함한다. 복호화와 해시 검증 전에
수신 파일을 게시하거나 저장 완료를 통지하지 않는다. 동일 파일 재전송은 암호문 캐시를 재사용한다.
캐시는 임시 파일 기록·sync·close 이후 독점 hard link로 .complete 파일을 게시한다.
이전 .bin 캐시가 정상이라면 그대로 계승하고, 부분 기록 파일은 게시하지 않은 채 재생성한다.
비대화형 서비스·창 실행 실패·중단은 사용자 거절로 기록하지 않는다. 명시적 승인/거절만 전송한다.
승인 스크립트는 Windows PowerShell 하위 프로세스에만 -ExecutionPolicy Bypass를 적용한다.
시스템/사용자 정책은 변경하지 않고 그룹 정책을 존중한다. 실행 실패 로그는 고정된 원인 분류와
종료 코드만 포함하며 stderr 원문·기기 이름·인증 비밀값을 기록하지 않는다.
send-phone-file.mjs 일반 전송은 owner 전용 GET /api/deliveries/:id로 작업 기록과 저장소를 확인한다.
작업 기록 없이 완성된 pc-phone 암호문만 남았다면 전송 ID·방향·파일 메타데이터를 확인하여
작업 기록을 복구한다. 이때 서버가 GCM 태그를 검증하는 것은 아니다. 태그는 수신 기기가 검증한다.
작업과 파일이 모두 없을 때만 job:null, storageChecked:true로 미접수를 확인한다.
신규/중복 POST와 조회 응답은 실제 저장된 파일에서 계산한 암호문 SHA-256·수신 키 지문을 포함한다.
PC는 현재 활성 키 집합과 정확히 일치할 때만 성공을 반환한다. 이전 기기용 파일이 먼저 저장되면
기존 작업/파일을 보존하고 새 전송 ID를 로컬에 먼저 저장한 뒤 현재 키로 전송한다.
교체 ID는 이전 ID와 현재 키 지문 집합에서 결정되는 UUIDv8 식별자이며 암호화 키가 아니다.
같은 경합을 겪은 동시 재시도는 같은 교체 ID로 수렴한다. 한 실행은 교체를 최대 세 차례 확인하며,
연결이 계속 바뀌면 오류로 종료하고 다음 실행에서 저장한 ID의 접수 상태부터 다시 확인한다.
조회 실패·404·손상 파일·검증 정보 누락은 미접수나 성공이 아니다. 이전 캐시는 덮어쓰지 않는다.
기존 HTTP 파일 API는 바이너리만 암호화한다. 목록·파일명·해시·크기·작업 메타데이터는 서버에 보인다.
DIANA.exe 기기 중계는 인증 후 RPC 본문과 응답 전체를 감싸므로 파일·미리보기·명령 내용도 암호화한다.
이 경로는 방향·요청 ID·2분 시각 범위·PC SQLite 재사용 기록을 검사한다. 토큰과 트래픽 크기는 중계에 보인다.
기기 폐기 이후 토큰은 PC/서버에서 거절된다. 이미 받은 파일과 키를 원격으로 지울 수는 없다.

신뢰 경계
자동 공개키 교환의 최초 연결에는 별도의 인증된 키 지문/SAS/PAKE가 없다.
따라서 최초 등록 때 능동적으로 키를 바꿔치기하는 악성 중계까지 방어한다고 주장하지 않는다.
정상 최초 연결 후 중계 저장소의 파일 바이너리만 유출돼도 해당 키 없이는 복호화할 수 없다.
완전한 Zero-Knowledge 또는 모든 MITM 차단 기능으로 표기하지 않는다.
6자리 코드와 PC 승인만 유지하는 UX에서 이 경계는 남는다. PAKE·15분 잠금 정책 변경은 포함하지 않는다.
단말·Windows 사용자 계정이 침해되거나 상대 단말이 이미 평문을 받은 경우는 보호 범위 밖이다.
원문, 로컬 결과물과 이메일 전달 경로는 기존 정책을 따른다. 이 기능은 이메일 암호화가 아니다.

Android 화면
MainActivity, PairedActivity 및 문서 대화상자는 표시 전 FLAG_SECURE를 설정한다.
시스템 화면 캡처/최근 앱 미리보기/비보안 디스플레이 보호는 OS가 집행한다.
다른 앱으로 파일을 열었을 때 그 앱의 화면, 외부 카메라, 루팅된 OS까지 통제하지 않는다.
계측 화면 캡처는 보호된 앱 화면이 가려질 수 있으며 레이아웃 검사는 View 단위로 유지한다.

업그레이드 및 배포
이 PR은 운영 배포나 기존 설치 앱 교체를 수행하지 않는다.
실제 반영 시 중계 서비스·PC·Android를 함께 호환 버전으로 준비하고 별도 시험 기기로 먼저 연결한다.
일반 문서는 키가 없는 기존 연결과 평문 전송으로 자동 후퇴하지 않는다. 기존 기기는 재연결해야 한다.
설치 순환 문제를 피하려면 send-phone-file.mjs --app-update로 공개 배포 APK를 먼저 전달한다.
owner 전용 /api/app-updates/:id는 파일 업로드를 받지 않고, 서버 배포 목록 android/legacy.android의
파일 경로·크기·SHA-256과 실제 배포 파일을 확인하여 이미 공개된 APK만 기존 수신 경로로 제공한다.
평문 예외는 명시된 공개 설치 파일뿐이다. APK 확장자로 바꾼 임의 문서나 미등록 APK는 거절한다.
Android는 공개 설치 파일 표시·APK 형식·해시·길이를 확인한다. 설치는 사용자 승인 및 Android의
패키지명/서명 검증을 거친다. 배포 관리자는 기존 설치와 같은 패키지명·서명의 새 버전을 게시해야 한다.
이미 평문으로 중계에 저장된 과거 파일은 이 변경으로 소급 암호화되지 않는다. 전환 전에 만료·정리한다.
기존 브라우저 콘솔은 키를 갖지 않으므로 파일 수신을 연결된 앱으로 안내한다.
로컬 주소로 우회하는 구형 직접 페어링은 거절하며 새 연결은 PC 승인 중계 경로를 사용한다.
중계 실행 소스는 현재 tests/helpers/paired-relay.mjs이며 향후 배포 시 이 변경도 포함해야 한다.
운영 반영 전 실제 휴대폰 화면 캡처 차단, 화면 회전/프로세스 종료 후 재시도, 승인/거절/만료,
기기 폐기, 재연결, 최대 크기 양방향 전송을 별도 시험 서비스에서 확인한다.
