# 문서 메일 연결

기본값은 `MAIL_MODE=dry-run`입니다. 실제 메일 서버에 연결하지 않고, 첨부파일까지 포함한 `.eml`을 프로젝트의 `.local/outbox`에 저장합니다. `.eml`은 메일 프로그램에서 열어 확인할 수 있습니다. 화면의 테스트 메일 생성은 실제 발송 완료를 뜻하지 않습니다.

현재 구현은 서버의 환경변수를 이용하는 SMTP 전송 어댑터입니다. **브라우저에서 Google/Microsoft 계정을 연결하고 동의를 받는 OAuth 가입·연결 UI는 아직 구현하지 않았습니다.** OAuth 토큰은 관리자가 외부에서 발급해 설정해야 합니다. `configured` 표시는 설정 형식이 준비되었다는 뜻이며, 계정 인증이나 수신함 도착을 검증한 결과가 아닙니다.

## 공통 설정

실제로 보내려면 로컬 `.env`에 `MAIL_MODE=smtp`를 명시하고 아래 제공업체별 설정을 입력한 뒤 에이전트를 다시 시작합니다. 비밀값은 소스 저장소·웹 화면·오류 메시지에 넣지 않습니다.

```dotenv
MAIL_MODE=smtp
MAIL_PROVIDER=gmail
MAIL_AUTH=oauth2
SMTP_USER=your-address@gmail.com
MAIL_FROM=your-address@gmail.com
MAIL_FROM_NAME=AI 원격비서
SMTP_ACCESS_TOKEN=replace-with-authorized-access-token
# 선택: 액세스 토큰 만료 시각, Unix 밀리초
# SMTP_TOKEN_EXPIRES=...
```

`MAIL_FROM`은 생략하면 `SMTP_USER`를 사용합니다. 인증 계정과 다른 발신 주소는 제공업체가 허용한 별칭/Send As 권한이 필요합니다. 수신자는 이름·쉼표·줄바꿈이 없는 단일 이메일 주소만 지원합니다.

첨부 원본 크기의 기본 상한은 15MiB입니다. `MAIL_MAX_ATTACHMENT_BYTES`로 최대 20MiB까지 설정할 수 있지만 MIME 인코딩 후 크기는 더 커지므로 제공업체의 한도도 적용됩니다. 지원 문서는 `.docx`, `.xlsx`, `.pptx`, `.pdf`, `.txt`, `.md`, `.csv`, `.tsv`, `.json`입니다.

## Gmail / Google Workspace

`MAIL_PROVIDER=gmail`은 `smtp.gmail.com:465`, TLS를 사용합니다. OAuth2 SMTP 토큰은 `https://mail.google.com/` 범위로 발급해야 합니다. SMTP 범위는 메일 전송 이상의 넓은 권한을 포함하므로 공개 제품으로 확장할 때 Google의 앱 검증과 사용 정책을 확인해야 합니다. 이 프로젝트에는 Gmail API 전송 어댑터가 없습니다. [Google 공식 XOAUTH2 문서](https://developers.google.com/workspace/gmail/imap/xoauth2-protocol)

액세스 토큰만 설정하면 만료 시 외부에서 갱신해야 합니다. Gmail에 한해, 사전에 동의받은 refresh token과 다음 값을 함께 설정하면 Nodemailer가 액세스 토큰을 갱신할 수 있습니다. 이 과정도 최초 사용자 동의를 대신하지 않습니다. [Nodemailer 공식 OAuth2 문서](https://nodemailer.com/smtp/oauth2)

```dotenv
MAIL_AUTH=oauth2
SMTP_REFRESH_TOKEN=replace-with-refresh-token
SMTP_CLIENT_ID=replace-with-google-client-id
SMTP_CLIENT_SECRET=replace-with-google-client-secret
```

Gmail 계정 정책상 앱 비밀번호가 허용되는 경우에는 `MAIL_AUTH=password`, `SMTP_PASSWORD=앱비밀번호`도 사용할 수 있습니다. 일반 로그인 비밀번호를 넣는 방식으로 안내하지 않습니다. Workspace 관리 정책에 따라 사용 가능 여부가 다릅니다. [Google 공식 SMTP 안내](https://knowledge.workspace.google.com/admin/gmail/send-email-from-a-printer-scanner-or-app)

## Outlook.com / Microsoft 365

개인 Outlook.com 계정은 `MAIL_PROVIDER=outlook`을 사용합니다. `smtp-mail.outlook.com:587`로 STARTTLS와 OAuth2 인증을 수행합니다. [Microsoft 공식 Outlook.com 설정](https://support.microsoft.com/en-us/outlook/pop-imap-and-smtp-settings-for-outlook-com)

Microsoft 365 회사 계정은 `MAIL_PROVIDER=microsoft365`를 사용합니다. `smtp.office365.com:587`과 STARTTLS를 사용합니다. 이 두 어댑터는 `MAIL_AUTH=oauth2`만 허용합니다. 회사 계정의 SMTP AUTH 사용 여부, 보안 기본값과 인증 정책은 조직 관리자가 확인해야 합니다. 특정 날짜를 근거로 모든 Microsoft 365 조직의 비밀번호 인증 상태를 단정하지 않습니다. [Microsoft 공식 SMTP AUTH 설정](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/authenticated-client-smtp-submission), [회사 SMTP 설정](https://learn.microsoft.com/en-us/exchange/mail-flow-best-practices/how-to-set-up-a-multifunction-device-or-application-to-send-email-using-microsoft-365-or-office-365)

사용자 위임 방식의 토큰 발급에는 Microsoft Entra 앱 등록과 `https://outlook.office.com/SMTP.Send` 동의가 필요합니다. 갱신 토큰을 발급받으려면 `offline_access`도 사용합니다. 현재 Microsoft 토큰 발급·갱신은 외부에서 수행하고 유효한 `SMTP_ACCESS_TOKEN`을 설정합니다. Gmail용 refresh 설정을 Microsoft 토큰 갱신에 사용하지 않습니다. [Microsoft 공식 OAuth 절차](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth)

## 네이버 메일

네이버 메일 설정에서 SMTP 사용을 켜고, 네이버 로그인 2단계 인증과 애플리케이션 비밀번호를 설정합니다. `SMTP_PASSWORD`에는 로그인 비밀번호 대신 발급된 앱 비밀번호를 넣습니다. 서버는 `smtp.naver.com:465`, TLS입니다. [네이버 공식 비밀번호 정책 안내](https://help.naver.com/service/30029/contents/24347), [공식 SMTP 설정 안내](https://help.naver.com/service/30029/contents/21341?lang=ko&osType=PC)

```dotenv
MAIL_PROVIDER=naver
MAIL_AUTH=password
SMTP_USER=your-id@naver.com
MAIL_FROM=your-id@naver.com
SMTP_PASSWORD=replace-with-naver-app-password
```

## 회사 자체 메일 서버

메일 관리자가 제공한 SMTP 서버 이름·포트·인증 방법을 직접 입력합니다. 아래는 설정 형식 예시이며 실제 서버가 아닙니다. `SMTP_SECURE=false`는 STARTTLS로 반드시 암호화한 뒤 전송한다는 뜻입니다. 평문 인증을 허용하지 않습니다. TLS 1.2 이상과 서버 인증서 검증을 강제하며, 인증서 검증을 끄는 옵션은 제공하지 않습니다.

```dotenv
MAIL_PROVIDER=custom
SMTP_HOST=smtp.company.example
SMTP_PORT=587
SMTP_SECURE=false
MAIL_AUTH=password
SMTP_USER=your-address@company.example
MAIL_FROM=your-address@company.example
SMTP_PASSWORD=replace-with-authorized-smtp-password
```

465 포트라면 `SMTP_SECURE=true`를 사용합니다. 자체 서버가 OAuth2를 지원하면 `MAIL_AUTH=oauth2`와 `SMTP_ACCESS_TOKEN`을 설정합니다. 서비스 비밀번호·앱 비밀번호·인증서 등 조직의 정책은 담당자 안내를 따릅니다.

## 전송 결과와 중복 방지

| 반환 상태 | 의미 |
|---|---|
| `dry_run` | 로컬 `.eml` 생성 완료. 외부 메일 제출 없음 |
| `submitted` | SMTP 서버가 해당 수신자에 대한 메일 제출을 수락함. 최종 수신함 도착은 별도 |
| `send_unknown` | 연결 끊김·프로세스 중단 등으로 제출 여부가 불확실함. 자동 재전송 금지 |
| `failed` | 입력·첨부 검증 실패, 준비 실패, 또는 명시적 SMTP 거부 |

`.local/mail-ledger`에는 작업 ID의 SHA-256 이름으로 배타적 claim 파일(`.json`)과 완료 receipt(`.result.json`)를 보관합니다. 각 파일은 새로 생성하고 디스크에 flush하며 덮어쓰지 않습니다. 같은 작업 ID와 내용은 기존 완료 결과를 반환합니다. claim만 있거나 기록이 불완전하면 `send_unknown`으로 막습니다. 같은 ID에 다른 수신자·첨부·제목·전송 모드를 지정해도 전송하지 않습니다.

SMTP 자체에는 이 모듈이 사용할 수 있는 제공업체 공통 멱등키가 없습니다. `Message-ID`를 고정해도 제공업체가 중복을 제거한다는 뜻은 아닙니다. `send_unknown`은 공급자 기록과 수신 결과를 확인하고 처리해야 합니다. 기록 파일을 지우거나 새로운 ID로 자동 재시도하지 않습니다. 테스트를 마친 뒤 실제 전송하려면 내용과 수신자를 다시 확인한 **새 작업**을 만듭니다.

`.local/outbox`에는 실제 첨부 내용이 있으므로 에이전트 계정이 접근하는 로컬 폴더로 관리합니다. 이 모듈은 메일 수신함을 읽거나 수신 메일에 따라 작업을 실행하지 않습니다.

## 코드 연결과 테스트

```js
import { sendDocumentMail, readMailConfig, getMailReadiness } from '../lib/mail.mjs';

const result = await sendDocumentMail({
  jobId: job.id,
  recipient: job.recipient,
  subject: job.subject,
  attachmentPath: document.absolutePath,
  attachmentName: document.fileName,
  expectedSha256: document.approvedSha256,
}, {
  env: process.env,
  dataDir: localDataDirectory,       // 생략하면 프로젝트 .local
  attachmentRoot: artifactDirectory, // 호출자가 허용한 문서 폴더
});
```

`options.config`를 쓰려면 같은 프로세스에서 `readMailConfig(env)`로 만든 객체를 전달합니다. 이 객체에는 비밀값이 있으므로 API에는 `getMailReadiness(env)` 결과만 내보냅니다. `sendDocumentMail`은 승인된 SHA-256과 실제 첨부 bytes를 비교하고, 검증한 bytes를 첨부하므로 검증 뒤 파일을 다시 경로로 읽지 않습니다. 작업 승인과 문서 폴더 접근 권한은 호출 에이전트에서도 검사합니다.

`node --test tests/mail.test.mjs`는 로컬 stream transport와 주입한 SMTP mock만 사용합니다. SMTP 서버·실제 수신자에게 메일을 보내지 않으면서 MIME 첨부, TLS 설정, 승인 해시, 헤더 주입 차단, 동시 실행, 불확실한 제출의 재전송 차단을 검증합니다.

공식 문서 확인 기준: 2026-10-22. 제공업체 정책과 조직 설정은 변경될 수 있습니다.
