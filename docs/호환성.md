# 원격 전원 켜기와 실행 조건

## 지금 구현한 범위

`gateway/`는 서버에 대기 중인 전원 요청이 있는지 확인하고, 로컬 환경변수에 등록한 PC의 MAC 주소로 Wake-on-LAN 매직 패킷을 전송하는 Node.js 24 프로그램이다. 기본은 `WAKE_DRY_RUN=true`라서 UDP 패킷을 보내지 않는다. BIOS, 네트워크 어댑터, 전원 관리, 공유기 설정을 자동 변경하지 않는다.

게이트웨이는 **깨울 PC와 별도로, 계속 켜져 있는 같은 LAN의 NAS·소형 PC·기타 Node.js 실행 기기**에서 돌아가야 한다. 꺼진 PC 안에서 실행되는 프로그램은 자기 자신에게 전원 신호를 보낼 수 없다. 지원 공유기의 내장 WoL 기능을 이용하는 방식도 가능하지만, 이 초기 버전은 공유기 제조사별 API 연결을 구현하지 않았다. 원격 기기를 깨울 때 같은 네트워크의 온라인 기기 또는 해당 기능을 지원하는 공유기를 이용하는 구성은 [TeamViewer의 WoL 설명](https://www.teamviewer.com/apac/global/support/knowledge-base/teamviewer-remote/remote-control/wake-up-a-device-remotely/)에서도 확인할 수 있다.

이 게이트웨이는 외부에서 집 PC로 들어오는 UDP 포트를 개방하는 구조가 아니다. 게이트웨이가 HTTPS API를 주기적으로 확인한 뒤 같은 LAN에 패킷을 전송한다. Node UDP 전송은 [Node.js 24 `dgram` 공식 문서](https://nodejs.org/docs/latest-v24.x/api/dgram.html)를 따른다.

## 어떤 PC를 깨울 수 있는가

| 조건 | 초기 버전의 의미 |
| --- | --- |
| 유선 LAN, WoL을 지원하는 메인보드·어댑터·드라이버 | 우선 확인할 시험 환경. 유선 연결만으로 지원이 보장되지는 않는다. |
| 절전·대기 상태 | 장치와 펌웨어가 해당 상태에서 깨우기를 지원하는지 실제 확인해야 한다. |
| 최대 절전·종료 상태 | OS 전원 상태, BIOS/UEFI, 네트워크 어댑터와 제조사 정책에 따라 달라진다. 모든 PC의 완전 종료 상태 전원을 켤 수 있다고 안내하면 안 된다. |
| 노트북·Wi-Fi·USB LAN 어댑터 | 기종과 전원 공급 상태에 따라 다르며 종료 상태에서의 동작을 보장하지 않는다. WoWLAN 지원 제품도 지원 전원 상태가 제한될 수 있다. |
| 콘센트 또는 멀티탭 전원 차단 | 네트워크 어댑터에 대기 전원이 공급되지 않으면 이 방식으로 깨울 수 없다. |
| 로그인·암호화·에이전트 시작 | 패킷 전송과 별개 조건. PC가 켜져도 로컬 파일 접근과 에이전트 실행이 가능할 때에만 후속 작업을 진행한다. |

Windows의 S0~S5 전원 상태와 Fast Startup은 [Microsoft 전원 상태 설명](https://learn.microsoft.com/en-us/windows/win32/power/system-power-states)을 참고한다. 특히 Windows 10의 종료·Fast Startup과 WoL 관계는 [Microsoft의 WoL 동작 설명](https://learn.microsoft.com/en-us/troubleshoot/windows-client/setup-upgrade-and-drivers/wake-on-lan-feature)에 정리되어 있다. 해당 문서의 Windows 10 설명을 모든 Windows 11 하드웨어의 보장으로 확대해서는 안 된다. 제조사별 확인 자료로는 [Intel Ethernet WoL 안내](https://www.intel.com/content/www/us/en/support/articles/000005793/ethernet-products.html)와 [ASUS WoWLAN 안내](https://www.asus.com/us/support/faq/1052580/)가 있다.

권장 첫 시연은 **사용자 소유의 호환 PC 1대, 유선 LAN, 별도 상시 게이트웨이, 검증된 절전 상태**다. 이 저장소를 만들면서 실제 전원을 켜거나 PC의 전원 설정을 변경하지 않았다. 자동 검증의 UDP 목적지는 `127.0.0.1`뿐이다.

## 연결 설정

프로젝트 루트의 `.env`에 다음 값을 넣고, Node.js 24에서 실행한다. MAC 주소와 브로드캐스트 주소는 게이트웨이 관리자만 로컬에서 설정한다. 서버 요청에 같은 이름의 값이 있어도 사용하지 않는다.

```dotenv
API_BASE_URL=http://127.0.0.1:8787
GATEWAY_TOKEN=replace-with-your-gateway-only-token
DEVICE_ID=home-pc
PC_MAC=02:12:34:56:78:9a
WOL_BROADCAST=255.255.255.255
WOL_PORT=9
WAKE_DRY_RUN=true
```

위 MAC 주소는 예시다. `PC_MAC`은 dry-run에서도 필요하다. 실제 신호를 보내려면 지원 하드웨어와 LAN 구성을 확인한 뒤 별도 게이트웨이에서 명시적으로 `WAKE_DRY_RUN=false`로 바꾼다. 예시 API 주소는 해당 컴퓨터에서 개발 서버를 실행할 때만 맞는다. NAS나 소형 PC에 배치하면 그 기기가 접근할 수 있는 **HTTPS API origin**으로 바꾼다. HTTP는 `localhost`, `127.0.0.0/8`, `::1` 같은 루프백 개발 주소만 허용하며 경로·URL 내 인증정보는 허용하지 않는다.

```powershell
node --env-file-if-exists=.env gateway/run.mjs
```

선택 설정은 `WOL_MIN_INTERVAL_MS`(기본 90000, 이보다 작게 설정 불가), `GATEWAY_POLL_INTERVAL_MS`(기본 5000), `GATEWAY_REQUEST_TIMEOUT_MS`(기본 10000)다. 요청 실패 시 간격을 늘려 최대 60초 후 재시도한다. 결과 보고에 실패하면 UDP를 다시 보내지 않고 결과 보고만 재시도한다. 신호 전송 시도 사이의 90초 제한과 중복 작업 억제는 실행 중인 프로세스 단위이며, 재시작 이후에도 완료 작업을 재발급하지 않는 것은 서버의 책임이다.

## API와 상태의 의미

- `GET /api/gateway/wake`: `Authorization: Bearer <GATEWAY_TOKEN>`, 응답은 `{ "job": { "id": "...", "deviceId": "home-pc" } }` 또는 `{ "job": null }`.
- `POST /api/gateway/wake/:id`: 동일 인증으로 `{ "status": "signaled" }`, `{ "status": "dry_run" }`, 또는 `{ "status": "failed", "error": "..." }`를 보낸다.
- `signaled`는 UDP가 패킷 전송을 받아들였다는 뜻이다. **PC가 온라인이 됐다는 뜻은 아니다.** 실제 준비 완료 여부는 PC 에이전트의 별도 접속·하트비트로 판단한다.
- `dry_run`은 신호를 보내지 않고 요청·응답 흐름만 확인한 상태다. 켜져 있는 PC에서 파일 작업을 검증하는 것과 전원 켜기를 검증하는 것은 별도다.
- 쿨다운 중인 새 작업은 실행하거나 실패 처리하지 않고 대기한다. API는 해당 작업을 다시 조회할 수 있도록 유지해야 한다.

토큰, MAC 주소, 파일 본문은 상태 로그에 출력하지 않는다. 게이트웨이는 임의 셸 명령이나 서버가 지정한 네트워크 목적지를 실행하지 않는다. 이후 파일 검색과 메일 발송 단계는 PC의 에이전트가 담당하며, 실제 메일 발송 전에 수신자와 파일을 확인하는 흐름이 별도로 필요하다.
