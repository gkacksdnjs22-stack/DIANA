# PC 로컬 요청 기록 v1

기존 PC 금융 검토 화면에서 선택적으로 사용하는 기능이다. 자연어를 자동 해석하는 기능이 아니며 연구 모델을 로딩하지 않는다. 0.3.3부터 저장 기록에서 **별도로 다시 확인한 문서 선택**으로 로컬 검토를 시작할 수 있다. 기록 저장만으로 검토가 실행되지는 않는다. 기록을 사용하지 않아도 기존 명시적 선택·PC 최종 승인·업무 저장 흐름은 그대로다. 새 웹사이트, Render 배포, Android 변경은 없다.

## 첫 기록 남기기

1. 새 소스 또는 새 Windows ZIP으로 PC 검토 화면을 연다. 사용 중인 worker는 사용자가 업무를 마친 뒤 정상 종료하고 새 버전으로 시작한다. 설치본을 자동 교체하지 않는다.
2. 왼쪽 **요청 기록 · 이 PC에만** → **새 요청 작성**을 누른다. 실제 하고 싶은 요청을 직접 입력한다. 작업 이름이나 선택 문서로 요청문을 자동 생성하지 않는다. 이 문장은 `사용자가 로컬에서 작성한 요청`이며 모바일/과거 요청의 원문이 아니다.
3. 연결할 등록 작업, 당시 확정 형식, 기록할 선택 동작을 확인한다. 최근 요청이 선택되어 있으면 해당 등록 작업의 선택을 초안으로 보여 준다. 요청 연결 없이도 기록할 수 있다. 실제 사용/검증용 가상 자료를 구분한다.
4. **당시 허용 후보·설정 확인**에서 전체 등록 후보를 본다. 수행 요청/질문·설명/취소/복합/판단 어려움을 고르고 대상·근거·지침·의도한 형식을 확인하거나 고친다. 각 인자에는 **없음**과 **미확인**이 있다. 클릭 초안이 정답으로 자동 확정되지 않는다.
5. **요청·후보·선택 확인하기**를 누른다. 요청 원문·전체 후보·설정·초안·본인 해석·연결된 업무 상태를 읽는다. 확인란을 선택하고 **확인하고 기록 저장**을 누른 때만 기록한다. 기록 저장·재읽기 완료 메시지를 확인한다. 업무 승인·실행·저장 성공과는 별개다.
6. **저장 기록 보기**에서 상세/변경 이력, **해석 수정**, **JSON 내보내기**, **이 기록 삭제**를 사용할 수 있다. 해석 수정은 당시 입력을 고정하고 v2, v3 등으로 추가한다. 요청 원문·당시 후보를 바꾸려면 새 기록을 작성한다. 전체 삭제는 모든 해석 버전의 본문을 삭제하며 재전송 방지용 ID/삭제시각만 남긴다. 내보낸 JSON 사본은 자동 삭제하지 않는다.

작성 중 입력·선택·형식이 바뀌면 확인이 풀린다. 후보/등록 설정 변경은 주기적으로 확인하며, 마지막 저장 시점에도 직렬 worker 경계에서 다시 검사한다. 새 확인본을 만들면 같은 기록의 이전 확인본은 무효다. 확인본은 10분 뒤 만료되고 worker 재시작 후에는 다시 확인해야 한다. 저장 응답이 유실되면 같은 확인본의 재전송은 같은 저장 결과를 반환한다. 실패를 성공으로 표시하지 않으며, 실패 후 목록에서 실제 결과를 확인할 수 있다.

## 기록에서 문서 검토하기 · 0.3.3

1. **저장 기록 보기**에서 기록 상세를 열고 **이 선택으로 문서 검토**를 누른다. 최근 모바일 요청이나 연결된 작업이 없어도 사용할 수 있다. 표시되는 요청문은 사용자가 작성한 원문이며 실행 명령으로 해석하지 않는다.
2. 과거 기록과 현재 후보·설정을 구분해서 확인한다. 사용자 본인 확인에 선택되어 있고 현재도 허용된 ID만 초안으로 표시한다. 현재 대상·근거 한 개 이상·지침·형식을 직접 선택한다. 없음·미확인 값이나 사라진 문서는 자동으로 채우지 않는다. 기록의 의도가 질문·취소·복합·미확인이거나 동작이 보완·변환이어도 원래 기록은 그대로 보존한다.
3. **현재 문서 상태 확인**을 누르면 서버가 현재 허용 역할·실제 파일·버전·내용 해시를 확인한다. 과거 후보 해시와 현재 선택 문서 상태를 읽는다. 선택을 수정하면 이전 확인이 해제된다. 문서·권한·후보가 바뀌면 최신 상태로 다시 확인해야 한다. 브라우저가 보낸 경로나 해시로 권한을 인정하지 않는다.
4. 표시된 선택에 대한 별도 검토 요청 확인란을 선택한 뒤 **검토 시작**을 누른다. 실행 동작은 `checklist_review`이며 문서 읽기와 검토 결과 확인까지만 수행한다. 보완·변환·파일 생성·최종 승인·업무 저장은 하지 않는다.
5. 항목별 판단·근거·미해결 항목과 실제로 읽은 원문을 확인한다. 모든 항목 충족과 근거 부족 등 추가 확인 필요를 구분하며, 권한 거부·문서 변경·코어 오류·빈 응답은 검토 완료로 표시하지 않는다. **실행 정보·문서 버전**을 펼치면 실행 ID, 연결 기록 버전, 현재 입력 스냅샷을 볼 수 있다. 정상 검토 완료도 업무 저장 성공을 뜻하지 않는다.
6. 같은 기록의 **로컬 검토 이력**에서 저장 결과를 다시 열 수 있다. 응답 유실이나 저장 상태 불확실 시 **같은 실행 ID의 결과 확인**으로 확인하며 자동 재실행하지 않는다. 시작 흔적만 있고 확정 결과가 없는 실행은 미확정으로 보존한다. 새 검토는 별도의 선택 확인이 필요하다.

기존 worker의 직렬 처리·잠금 경계를 사용한다. 승인 대기·저장 중·미확인 상태 보고 등 충돌 가능한 작업이 있으면 새 검토를 거부하며 기존 승인 계획을 취소하거나 교체하지 않는다. 이때 저장된 검토 이력은 조회할 수 있다. 종료는 기존 PC 실행기의 정상 종료 절차로 진행 중 처리를 정리한다. 검토 출처는 PC 로컬 명시 선택이며 모바일 job이나 서버 업무 완료 상태를 새로 만들지 않는다.

## 저장 위치와 형식

실제 사용 중인 worker 설정의 `stateDir` 뒤에 `.request-records`를 붙인 **별도 로컬 폴더**다. 예를 들어 stateDir이 `C:\...\state`이면 `C:\...\state.request-records`다. 브라우저가 폴더를 지정할 수 없다. 문서 입력 루트·업무 출력·일반 파일 루트·worker 상태·등록 저장소와 겹치면 기록 저장을 거부한다. 경로·링크·일반 파일 여부를 기존 파일 검사로 확인한다. 수집을 열기 전에는 폴더를 만들지 않는다.

파일은 `<UUID>-v1.json`, `<UUID>-v2.json`처럼 배타 생성한다. 각 버전은 이전 버전의 SHA-256을 포함한다. 삭제 후 `<UUID>-deleted.json`만 남겨 같은 ID의 과거 저장 재전송이 기록을 되살리지 못하게 한다. 파일은 JSON 평문이며 OS 계정의 로컬 파일 권한에 의존한다. 디스크 암호화나 별도 사용자 인증을 새로 제공하는 기능은 아니다. 다른 프로그램/백업이 만든 사본은 관리 범위 밖이다.

| 필드 | 의미 |
| --- | --- |
| schema_version / record_id / version / previous_hash | 기록 스키마, UUID, 수정 이력 연결 |
| created_at / authored_at / confirmed_at | 최초 기록 작성 수신·원문 최초 확인화면 수신·사용자 저장 확인 시각 |
| authored_time_basis | `first_server_preview_of_user_local_text`: 타이핑 시작 시각이나 모바일 원문 작성 시각으로 추정하지 않음 |
| input_path / request_origin | PC 로컬 기록 입력란 / 사용자가 로컬에서 새로 작성 |
| data_origin / purpose | 실제 사용 또는 검증용 가상 자료 / 사용자 확인 개발자료 후보 |
| input | schema_version, 요청 원문, 확정 형식 context, 허용 후보 ID·이름·alias·역할 |
| input_snapshot_hash | input 전체의 키 정렬 canonical JSON을 UTF-8 SHA-256으로 계산 |
| catalog_snapshot / catalog_hash | 당시 후보 전체·버전·분류·등록 작업과 범위 설명·등록 revision |
| selection / explicit_selection_draft | 기록할 작업·동작·형식 및 해당 등록 작업의 대상·근거·지침 초안 |
| linked_task_id / linked_job_id | 연결 가능한 등록 작업 및 현재 로컬 화면의 실제 요청 ID, 없으면 null |
| execution_observation | 해당 요청의 관찰 시각·상태·동작·형식·저장/재읽기 여부. 사용자 의도와 별개이며 이후 자동 갱신하지 않음 |
| raw_user_confirmation | 사용자 의도 및 인자별 selected / none / unknown 구분 |
| annotation_provenance | `user_self_confirmation`, 독립 A/B나 제3자 검토 아님 |
| contract_annotation | 항상 `partial_needs_review`, output 및 utf16_mentions는 null. null 정답을 의미하지 않음 |
| app_version / contract_version / record_version | 앱 배포/소스 버전 표기, 금융 review 입력 v1, 기록 v1 |

후보는 `FinancialDocuments.candidates()`의 현재 권한 필터 결과와 기존 PC 등록 메타데이터를 직렬 경계에서 결합한다. 선택된 문서만 저장하지 않는다. PC 파일 시스템을 검색하지 않으며, 요청 기록의 후보 스냅샷에는 문서 본문·경로·키·승인 토큰을 가져오지 않는다. 별도 검토를 명시적으로 시작한 경우의 본문 보관은 아래 로컬 검토 이력에 한정한다. 기존 목록에 alias 등록 기능이 없으므로 `aliases=[]`와 미등록 범위를 명시한다. 역할은 현재 PC 선택 용도와 등록 작업에서 실제 사용한 역할을 나타내며 새 ACL 권한을 부여하지 않는다. 실제 후보가 0개면 빈 목록 그대로이며 필수 문서를 만들어 채우지 않는다. 조회 실패를 빈 목록으로 위장하지 않는다.

후보 이름/alias가 연구 입력의 길이 한도를 초과하거나 민감 패턴이 있으면 수집을 거부하고 기존 앱은 계속 사용할 수 있다. 원문 요청의 인증키/토큰·Windows 절대 경로 패턴을 거부하지만 모든 비밀이나 개인정보를 찾아내는 검열기는 아니다. 사용자가 문서 본문·비밀·불필요한 개인정보/경로를 요청란에 붙이지 않아야 한다.

UTF-16 구간은 이름의 첫 등장이나 선택 클릭으로 생성하지 않는다. emoji/한글을 포함한 요청 원문을 보존하며 깨진 surrogate는 거부한다. 사용자가 인자를 선택해도 원문에 언급이 없을 수 있으므로 구간은 미주석으로 남긴다. status/intent/issues도 사용자의 쉬운 의도 선택에서 자동으로 전체 계약 정답을 만들지 않는다. 연구 모델 입력/정답으로 자동 사용하지 않는다.

### 별도 로컬 검토 이력

검토 실행은 `stateDir.request-reviews`에 별도로 보관한다. 예를 들어 `C:\...\state.request-reviews`이며 브라우저가 저장 경로를 지정할 수 없다. 실행 ID별 `<UUID>-start.json`, `<UUID>-result.json`, `<UUID>-exposure.json`을 사용한다. 시작 기록에는 원래 `record_id/version/hash`, 당시 입력 해시, 현재 선택·문서 버전/해시·정책 해시·시작 시각을 남기고, 결과에는 종료 시각과 `completed`/`failed` 상태 또는 진단을 남긴다. 미확정 실행은 시작 기록으로 보존한다. 원래 요청 기록과 본인 해석을 검토 결과로 덮어쓰지 않는다. 요청 기록의 `execution_observation`은 당시 연결 업무 관찰값이고, 이 별도 검토 이력과는 다르다.

검토 결과에는 항목·근거·미해결 내용과 **실제로 읽은 대상·근거·지침 본문**을 포함한다. 이 파일도 JSON 평문이며 PC의 OS 계정 권한으로 보호된다. 본문·결과는 외부 서버·모바일·분석 로그에 보내지 않는다. 기존 JSON 읽기 제한 2,000,000바이트 안에 실행 메타데이터가 들어갈 여유를 두기 위해, 검토 결과 전체의 UTF-8 JSON 크기를 1,500,000바이트로 제한한다. 초과하면 `LOCAL_REVIEW_RESULT_TOO_LARGE` 실패로 기록하며 본문이나 근거를 잘라 성공으로 저장하지 않는다. 업무 출력 파일을 저장하는 기능은 아니다. 요청 기록을 삭제하면 연결된 검토 실행·결과·노출 파일도 삭제한다. 외부 백업·내보낸 사본은 자동 삭제하지 않는다.

노출 기록은 인증된 로컬 화면에 실행 결과를 반환한 시점을 남긴다. 실제로 사용자가 읽었다는 증명은 아니다. 이후 본인 해석을 수정하면 `review_exposure_at_preview`와 `review_exposure_at_save`에 당시 노출 이력을 남긴다. 검토 결과는 사용자 정답으로 자동 확정하지 않으며 `contract_annotation.state=partial_needs_review`, 미주석 UTF-16 구간과 status/intent/issues를 유지한다. 독립 A/B 주석·제3자 검토로 바꾸지 않는다.

## 로컬 보안과 업무 분리

`POST /api/request-records`는 기존 127.0.0.1·Host/Origin/Fetch-Site·임시 Bearer 세션·JSON 제한을 재사용한다. 본문은 32KB 이하이며 각 동작은 정확한 키만 받는다. 브라우저의 `path`, 문서 본문, 승인 토큰 등 추가 필드는 거부한다. 목록·상세도 같은 세션으로만 읽는다. JSON 내보내기는 인증된 상세 응답으로 브라우저에서 생성하는 로컬 다운로드다. 외부 API/모바일/분석 로그로 기록을 보내지 않는다. 기존 `/api/view` 응답이나 desktop stdout 상태에 기록 내용을 섞지 않는다.

기록 작성·저장 동작은 prepare/approve/execute, 작업 등록, worker tick, 모델을 호출하지 않는다. 별도 `review-*` 동작만 동일 worker와 `FinancialDocuments`의 읽기 전용 검토 경계를 사용한다. 현재 정책·허용 ID·실제 문서와 해시를 재검사하고 기존 검토 코어를 호출하지만 승인 토큰이나 업무 출력물을 만들지 않는다. 대기 승인을 취소하거나 다른 작업을 실행하지 않는다. 저장소 문제는 기록/검토 오류로 응답하며 업무 저장 성공 메시지로 대체하지 않는다.

## intake로 옮기기 전에 필요한 것

이 기록은 실제 사용자 본인 확인 개발자료 **후보**다. 인간 A/B나 final 관리자가 없어도 기록을 시작할 수 있지만 독립 평가 준비 완료는 아니다. 새dev/final 자동 편입, train 로더 연결, 추론·채점·학습·freeze가 없다.

기록에서 가져올 수 있는 것은 원문·당시 후보/설정·입력 해시·로컬 출처/시각·사용자 확인과 수정 이력이다. `evaluation-intake-v1`로 정식 이전하려면 별도로 연구 사용권한, 원천업무/회사/문서계보/표현가족·부모, 가명화/노출 이력, 분할 배정, 주평가/확장 조건, 숙련된 독립 A/B 주석과 필요한 제3자 조정, UTF-16 구간·status/intent/issues, 누수 감사 및 동결이 필요하다. 본인 확인을 A/B 중 하나로 자동 인정하지 않는다. 절차 시험에 노출된 기록의 새dev 편입 여부는 따로 결정한다. 기존 sealed test와 새final 본문은 이 기능에 연결하지 않는다.

## 실행과 번들

소스 실행은 기존 명령 그대로다.

```powershell
cd C:\work\diana
npm.cmd run finance:worker -- --config "검토한 worker.json의 절대 경로" --no-open
```

콘솔에 표시된 PC 검토 주소를 연다. `--console` 모드는 기존 콘솔만 사용하므로 기록 화면이 없다. Windows에서는 새 `DIANA-PC-0.3.3-win-x64.zip` 전체를 **별도 폴더**에 풀고 `DIANA.exe`를 실행한다. 새 파일만 기존 설치본 위에 덮어쓰지 않는다. 기존 worker가 실행 중이면 정상 잠금 정책에 따라 두 번째 worker가 시작되지 않는다. 기존 연결 설정 재사용은 기존 실행기 정책을 따른다.

0.3.2는 Windows AppData의 공용 `desktop.json`을 문서 경로 검사로 차단해 `DESKTOP_START_FAILED`가 나던 시작 오류를 수정한다. 사용자가 지정한 실행기 설정만 별도의 크기·UTF-8·파일/상위 폴더 링크·동일 파일 검사로 읽으며, 일반 문서 수집의 AppData 제한은 완화하지 않는다. 기존 공용 설정이나 작업 설정을 다시 작성할 필요는 없다.

최근 업무 요청과 연결할 등록 작업이 모두 없는 경우에도 ‘새 요청 작성’을 열 수 있도록 수정했다. 업무 요청·승인·실행 없이 요청 기록을 시작할 수 있다.

0.3.3은 위 0.3.2 수정을 유지한다. 번들에는 기존 요청 기록 서버/화면에 더해 `record-reviews.mjs`, 화면의 `local-review.mjs`, 동일 adapter·worker의 읽기 전용 검토 연결, viewer/CLI/desktop 연결, 스타일 및 사용법이 반영된다. 빌드는 고정 whitelist를 사용하며 수집 기록·실제 문서·키·연구 모델을 포함하지 않는다. 빌드 API의 `updateDevPicker:false`는 기존 개발 폴더 선택기까지 보존하기 위한 별도 산출 옵션이다.

## 검증 범위

가상 자료로 저장 전 미저장, 후보/설정 변경 시 거부, 요청 재확인 시 이전 확인 취소, 없음/미확인, emoji 원문·미주석 구간, 저장 재읽기/재시작/수정/중복/삭제, 쓰기 충돌, 임의 경로/인증 없는 접근 거부를 검사했다. 실제 로컬 후보 조회와 연결한 가상 업무 검사에서 요청 기록이 대기 승인·외부 통신·업무 출력에 영향을 주지 않고, 이후 기존 명시적 승인이 정상 동작함을 확인했다. 실제 사용자 문서로 실행·승인·저장하지 않았다.

0.3.1 당시 브라우저 UI 자동화는 인앱 탭 연결 종료 후 Windows 현재 URL 확인 실패로 중단됐고, 그 버전의 화면 클릭 전체 E2E 검증은 미완료였다. 서버/API 및 UI 확인 상태 모듈 검사를 실제 브라우저 사용 검증으로 표현하지 않는다. 기존 사용 worker를 종료하지 않았으며 가상 QA 서버만 정리했다. 이후 버전의 실제 화면 검증은 아래에 별도로 기록한다.

### 0.3.2 시작 오류 및 첫 기록 검증

0.3.1의 위 UI 검증 제한을 보완했다. 별도 가상 자료와 localhost 중계로 최종 0.3.2 번들의 실제 `WorkerSession`을 실행해 AppData 경로의 설정 읽기·ready·연결을 확인했다. 실제 브라우저에서 최근 업무 요청 0건 및 작업 미연결 상태로 새 기록을 열고, 가상 요청·후보 3개·본인 해석을 확인한 뒤 저장·재읽기 완료와 목록 1건을 확인했다. 디스크 JSON의 가상 자료 구분·후보 스냅샷·미주석 계약·연결 업무 null을 대조했고 업무 출력 파일은 0개다. 테스트 실행기는 정상 종료했다.

설정·승인·등록·잠금·요청 기록 관련 회귀 90개와 최종 UI 수정 후 요청 기록·viewer 21개가 통과했다(21개는 90개에 포함되는 재검사). Windows 네이티브 인자/설정 재사용 검사도 통과했다. 최종 번들 88개 파일 해시와 whitelist 소스 일치를 확인했다. 사용자 기존 설정·설치본·worker와 연구 모델은 변경하지 않았다. 상세는 `.local/desktop-startup-fix-verification/verification.json`, 가상 기록 저장 화면은 같은 폴더의 `record-saved.png`다.

### 0.3.3 로컬 검토 검증 (2026-10-28)

가상 자료의 서버·코어·기존 모바일/PC 승인·저장·잠금·기록 회귀 158개와 검토 전용/화면 판정 18개, 총 176개가 통과했다. 명시 선택 전달, 정상 검토와 근거 부족/진단 구분, 권한·문서 변경 거부, 중복/재시작/불확실 실행, 승인 계획 보존, 종료 처리, 인증·Origin·경로/이력 변조 거부, 1.5MB 결과 제한을 검사했다. 테스트 로그는 `.local/record-review-verification/regression.tap`, `explicit-ui.tap`에 있다. 별도의 중복 sandbox 검사에서 localhost EACCES·hardlink EPERM이 발생했으며, 권한이 허용된 위 전체 검사에서는 모두 통과했다.

최종 ZIP을 새 폴더에 압축 해제하고 90개 파일 해시·whitelist 소스 일치를 검증한 뒤, 실제 번들의 Windows `WorkerSession`과 Node/Python으로 실행했다. 별도 QA AppData 설정과 localhost 가상 중계만 사용했다. 실제 브라우저에서 최근 모바일 요청 0건·등록 작업 미연결 상태의 새 기록을 저장했고, 저장 직후 검토 실행과 업무 출력은 0건이었다. 원래 `question/patch` 기록을 그대로 보여 준 뒤 별도 `checklist_review` 선택을 재확인했다. 형식 변경 시 확인이 무효화됐고, 명시적 시작 클릭 후 세 가상 문서의 실제 검토 결과·근거·미해결 항목·본문을 확인했다. 결과는 충족, 근거 있는 보완 필요, 근거 부족을 구분했다.

결과 열람 후 해석을 v2로 수정했을 때 노출 이력 1건과 부분 주석이 유지됐고, v1 파일 해시와 당시 입력은 변경되지 않았다. 화면 재로드 후 v1 검토 이력을 조회해도 실행은 총 1건이었다. 업무 출력 0개·모바일 job/완료 보고 0건·가상 원문 해시 유지·QA worker 정상 종료를 확인했다. 기존 설치본·공용 설정·사용 중 worker·연구 보고서는 보존했다.

번들: `.local/financial-desktop-builds/2026-10-28T05-14-13-537Z-1ca0fd06/DIANA-PC-0.3.3-win-x64.zip` (옆 `.sha256` 파일 포함). 종합 근거는 `.local/record-review-verification/verification.json`, 화면 증거는 그 파일의 `fixture_root` 아래 `selection-reconfirmation.png`, `review-result.png`, `history-result.png`다. 실제 화면 검증은 정상 검토 중 미해결 근거가 있는 경로를 다뤘고, 권한 거부·문서 변경·코어 오류·동시성은 서버/코어 검사로 확인했다. 다른 PC 실기기 검증과 코드 서명은 아직 수행하지 않았다.
